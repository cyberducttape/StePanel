## What every job proves

Each job installs a published release, upgrades it to the candidate, and then:

1. checks the candidate panel and worker, `/readyz`, operator-managed
   settings, `dr-check`, a control-plane backup and a dry-run restore;
2. runs a deliberately broken candidate whose services damage the database,
   and requires the installer to restore the upgraded candidate and its
   database (installer rollback before commit);
3. undoes the committed upgrade with the procedure in
   [COMPATIBILITY.md](../COMPATIBILITY.md#rollback): restore the configuration
   the installer kept for the replaced release, restore the pre-migration
   database snapshot, disable the root broker, and reinstall the previous
   release. The previous release must serve `/readyz` and its own
   `verify-audit` must accept the audit log, including the records the
   candidate appended;
4. upgrades the rolled-back host to the candidate again.

The "interrupt verification" jobs first start the candidate installer and kill
its whole process group with SIGKILL as soon as its journal records the
`verification` phase: the new binaries and units are in place and the
services have started on them, but the installer has not committed and no
rollback runs. A plain rerun of the candidate installer then has to complete
the upgrade, and the downgrade in step 3 must restore the configuration the
*first* (killed) attempt kept, not the candidate's file the rerun found.

## Defects found and fixed while building the matrix

- **The documented downgrade could not work.** Reinstalling v0.6.0 or v0.7.0
  after an upgrade stopped at once with "/etc/ste-panel.env contains an
  unsupported entry": those installers accept only `STEPANEL_*="…"` lines,
  and the current installer writes `RCLONE_CONFIG`, which every production
  install with an offsite target has. Nothing kept the earlier file. The
  installer now keeps the replaced release's environment file before it
  changes anything (`deploy/lib/install-upgrade-retention.sh`).
- **The downgrade procedure left the root broker enabled** on releases that
  predate it; the procedure now disables it.

## Fixtures

v0.6.0 and v0.7.0 cannot complete a fresh install as published on a current
Ubuntu 24.04 host, so no unmodified installation exists to upgrade:

- they run their local database helper through `sudo`, which their own
  service sandbox refuses (`sudo: unable to change to root gid: Operation not
  permitted`), so readiness never succeeds;
- with Caddy, the PHP packages they install pull in and start `apache2`, which
  holds port 80, so Caddy cannot start. Existing hosts of those releases run
  Apache.

[`upgrade-fixture.sh`](../../deploy/lab/upgrade-fixture.sh) therefore has two
modes. **helper** (QEMU guests) drops only the `STEPANEL_DBCTL` entry;
everything else is as published, including the systemd `LoadCredential`
database-credential handoff the upgrade must migrate. **container** also
rewrites that handoff, because the systemd container cannot expose
`LoadCredential` to the service. Each edit fails the job if it no longer
applies.

## Limits

One run per combination. Ubuntu 24.04 only; no AlmaLinux or Rocky guest, no
XFS or quota-enabled filesystem, no populated sites, databases or backups in
the previous release, and only the `verification` interruption point. A
QEMU guest is a disposable VM, not a physical host. The re-upgrade to the
same release reuses the configuration kept by the first upgrade, so settings
changed under the older release in between are not carried forward
(documented in COMPATIBILITY.md).
