# Database restore swap on a full filesystem (MySQL 8.0) — 2026-11-25

**Run:** [GitHub Actions 45528174769](https://github.com/cyberducttape/StePanel/actions/runs/45528174769), step "Fill the database filesystem as a restore swaps (MySQL 8.0)"  
**Source:** `f0783112`  
**Host:** GitHub-hosted Ubuntu 24.04 runner, MySQL 8.0 with binary logging, data directory on a 1,659 MiB loopback ext4 filesystem  
**Drill:** [`deploy/lab/dbctl-swap-enospc-smoke.sh`](../../deploy/lab/dbctl-swap-enospc-smoke.sh)

## What was done

A managed site database with a table, a view and a trigger was backed up
with `stepanel-dbctl dump`, then changed. `restore-dump` was started from the
backup. A watcher filled the data filesystem to 0 KiB free the moment the
restore record entered the swap phase, held it full for up to 45 seconds,
then freed it and ran `stepanel-dbctl reconcile`, as startup does.

## Observed

- The filesystem reached 0 KiB free as the swap started.
- MySQL logged an out-of-space condition during the swap.
- The swap stopped with `restore stopped during the swap; the next dump,
  restore or reconcile of this database finishes it`.
- After space returned, reconciliation rolled the swap forward. The database
  held exactly the backup's rows, the view and the trigger (which fired on a
  new insert); the site's own account could read and write, so the login
  fence was lifted; no `stepanel_restore_*` or `stepanel_retired_*` database
  and no restore record remained.

## Repeat and cleanup phase

CI run [45534504223](https://github.com/cyberducttape/StePanel/actions/runs/45534504223)
on `ed44a272` repeated the swap case with improved reporting: the server log
recorded out-of-space 4 times and the helper received it 3 times; the swap
stopped and rolled forward to the same final state. The same run filled the
filesystem when the swap had finished and cleanup began
(`STEPANEL_DB_ENOSPC_FILL_PHASE=done`): dropping the shadow and the retired
copy of the old tables completed while the filesystem was full, which needs
no new space, and the final state was correct.

## Limits

One pass on a CI runner with MySQL 8.0. The same drill runs in the KVM
`db-enospc` phase against the installed MariaDB; that result is recorded
separately. This is not physical-host power loss, and the shadow load itself is stopped by
the free-space watchdog before a true out-of-space write.
